# V1 系统架构与 V2 演进边界

状态：V1 已完成实现并通过全量验收。以下描述当前已交付的 V1 架构；V2 实时数据流与 React + TypeScript + Vite 页面交互处于规划阶段，范围见[路线图](roadmap.md)，不代表当前已运行的能力。

## 目标与范围

在当前机器上复用三台虚拟机组成的 Hadoop/Kafka 集群，完成 Retailrocket 历史行为回放、分布式采集、离线分析与交互展示。V1 以快速交付为优先，不依赖校园商城，不新增 Hive、HBase、Superset、独立 API 或前端应用。

需求与指标口径以 [requirements.md](requirements.md) 为准，版本范围见 [roadmap.md](roadmap.md)。领域术语见根目录 [GLOSSARY.md](../GLOSSARY.md)。

## 数据流与模块

1. 数据准备：获取 Retailrocket 原始文件并登记数据版本、文件校验值及行数。开发使用固定样本，验收处理完整行为数据。
2. 行为回放：Python 程序逐行将行为事件写入 Kafka。携带数据版本、源文件标识和源行号，形成稳定源记录标识；原始事件时间与回放时间分别保存。源行号在过滤之前分配。
3. 批量采集：回放前记录各分区起始 offset，确认发送完成后记录结束 offset；Spark 按固定范围读取，验证属于本批次的数据并写入 HDFS 原始层。未完整确认发送成功的批次不发布。源文件稳定标识用于处理发送重试产生的重复消息。
4. 参考数据导入：商品属性及分类树直接写入 HDFS，并与行为输入绑定为同一数据版本。
5. 清洗与关联：PySpark / Spark SQL 在 YARN 执行，生成 Parquet 明细、异常记录及质量统计。分类使用按事件时间关联的历史属性；无需处理的匿名属性 V1 不加载。
6. 指标与画像：计算全局统计、按日统计、访客每日行为和分类偏好等结果，保存在 HDFS。面向任意日期范围的独立访客、交集和画像需要保留访客粒度结果，不能将每日独立访客数相加。
7. 结果导出：将面向看板的结果导出为本机不可变 Parquet 批次目录，校验后切换当前成功批次。原始全量清洗与分类关联由 Spark 完成。
8. 交互展示：Streamlit + Plotly 提供页面，DuckDB 查询本机结果，执行日期筛选及必要的访客粒度聚合。缓存绑定批次和筛选条件；每次页面计算使用同一成功批次。

## 部署边界

- 三节点虚拟机：复用 Kafka、HDFS HA 和 YARN，Spark executor 通过 YARN 实际跨节点执行。
- 本机：回放程序、作业提交入口、结果目录及看板；使用固定运行环境，避免直接依赖宿主 Python 版本。
- 复用 HDFS 逻辑入口 hdfs://mycluster；Kafka 地址须确保宿主及所有执行节点均能解析和访问 advertised.listeners。
- HBase 不参与 V1，可在实施时确认依赖后停止以释放内存；保留既有集群数据和配置。
- 三个节点共享同一物理宿主，验收展示多节点执行，不宣称能够承受宿主机故障。
- V1 按受控的单任务顺序运行，不实现多用户同时导入、调度平台或常驻流处理。

## 批次与发布

批次登记数据版本、输入文件、Kafka topic/partition/offset 范围、各阶段记录数、状态和输出路径。处理流程为：准备、回放、采集、分析、校验、发布；任一阶段失败可记录并重试，失败结果不替换已发布结果。

批次隔离与源记录去重共同防止重跑累计。每个成功批次是指定数据范围的完整分析快照，不向上一成功批次追加指标。Kafka 用于采集传输；持久的重算依据是原始文件及 HDFS 落盘数据，不依赖 Kafka 无限期保留消息。

## V1 验收标准（已通过）

- 完整行为数据经过 Kafka；记录发送数、消费数、唯一源记录数及异常数，并提供一致性核对。
- 属性和分类文件成功导入并完成事件时间关联，未知分类计入质量摘要。
- 提供 HDFS 文件及 YARN 作业证据，确认实际分布式执行；不能以 local 模式代替最终验收。
- 四类页面和质量摘要可用，日期筛选、访客查询及分页符合需求口径；分母为零显示无数据。
- 同一批次重跑不使统计翻倍；构造失败批次后，先前成功结果仍可查看。
- 使用小型已知输入验证分类时点、重复消息、访客交集、跨日去重、日期筛选边界及空数据等核心规则。
- 提供从环境检查、数据准备到看板启动的可复现命令及演示步骤，记录数据来源和最终锁定版本。

## 已验证的运行环境

既有环境为 Hadoop 3.1.3、Java 8u212、Kafka 3.7.0，每节点 YARN 内存约 1536 MiB。已新增隔离的 CPython 3.11.16、Spark 3.5.6 / Scala 2.12 和匹配的 Kafka 连接器，不依赖宿主默认 Python。生产转换在 executor JVM 中执行，worker 节点无需 Python。实际资源配置、时钟约束及部署方式见[运行说明](operations/small-sample.md)，跨节点全量成功、失败恢复及发布验证见[验收证据](evidence/full/README.md)。

既有集群软件与配置未被替换；后续执行仍需核查节点、网络、磁盘和可用资源，不能将历史验收状态视为永久可用容量。

## V1 日期查询与结果一致性

日期分析按原始事件时间的 UTC 日期筛选，开始日和结束日均包含全天。
Spark 导出 `visitor_events`（event_date、visitorid、event 去重）供 DuckDB 在
整个范围重新按访客去重；范围独立访客不可由每日人数相加得到。购买关联是
范围内浏览/加购访客与购买访客的集合交集，允许逆序事件，不是严格漏斗。
无浏览或加购访客时相应比例显示“无数据”。质量页将可归属日期的记录数与
整个批次的采集核对分开展示；无效时间只能计入批次质量。
看板参数为发布 store，单次渲染固定一个成功批次快照及统一日期范围。

## V2 已实现边界与最终验收

React + TypeScript + Vite、Ant Design、ECharts 提供历史分析与本轮实时监控。FastAPI 绑定本机回环地址，页面每 2 秒读取 HTTP 缓存，不直接连接 Kafka，不因刷新启动 Spark。历史查询仍固定一个经过校验的不可变发布快照，实时指标明确展示本轮完整性。

单轮 worker 将已注册并核验的原始行为回放至独立 Kafka topic。Structured Streaming on YARN 按源身份精确去重，区分内容重复与源重试，分别累计有效访客及 UTC 事件趋势。两个有状态算子使用 HDFS 检查点和有界 RocksDB 原生缓存；没有 watermark，合法乱序与跨日状态不因时间截断丢失。每批不可变增量与累计快照提交后，驱动再次确认对应 checkpoint commit，才原子替换本机观察缓存。后台通过 SSH 读取此小文件及 Kafka 末端，不为每次轮询启动 HDFS CLI JVM。

回放游标表示连续、已获 Kafka ACK 的源行前缀。默认逐行持久化；全量部署可采用每 100 条或最多 1 秒持久化，并在暂停、停止、EOF 强制刷新。故障可能重发有界前缀，源身份去重保持业务结果不翻倍。手动恢复校验原 topic、输入及检查点，先停用旧拥有者，再继续同一轮次；损坏检查点显式报错。

完整轮次先排空积压、释放流作业，再执行历史 YARN 分析、导出、传回并完整校验发布。提前停止永不发布部分历史；失败保留旧发布快照，历史阶段可独立重试。产物永久保留，手动清理受保护路径见运行说明。

V1 的手动批处理仍遵循 [ADR 0002](adr/0002-kafka-batch-ingestion.md)，V2 的流批分阶段设计遵循 [ADR 0003](adr/0003-bounded-streaming-replay.md)。最终全量链路、至少 15 分钟正常负载和实际浏览器 ACK→首次可见 P95≤10 秒仍以 [V2 验收记录](operations/v2-acceptance.md) 的实测结果为准；未全部通过前不标记 V2 完成。
