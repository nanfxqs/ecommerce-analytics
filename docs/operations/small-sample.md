# Fixed Retailrocket historical replay

The initial real audit on 2026-10-19 found three existing AlmaLinux8.10 VMs, Hadoop3.1.3 HA, Java8u212, Kafka3.7.0 (Scala2.12), 1536MiB YARN memory per node, and about31GiB free per node. All three VMs were initially stopped. The existing cluster startup script started them; existing configuration and software were preserved. HDFS uses `hdfs://mycluster`. Kafka advertises `hadoop01`, `hadoop02`, `hadoop03`; the edge node and executor nodes resolve these. The host does not resolve them, so replay and submission run on the edge node.

The isolated added runtime is CPython3.11.16 and Spark3.5.6 with matching Scala2.12 Kafka connector3.5.6. The Python dependencies are pinned in `uv.lock`; the five added connector jars have SHA256 checksums in `scripts/connector-sha256.txt`. Existing Java is unchanged. Spark SQL transformations run in the executor JVMs, without requiring executor Python. Compatibility references: [Spark3.5.6](https://spark.apache.org/docs/3.5.6/) and [Kafka integration](https://spark.apache.org/docs/3.5.6/structured-streaming-kafka-integration.html).

For the maintained commands, follow [the README](../../README.md). The complete runner now requires `--references` and uses a publication store for the dashboard. Use `prepare --limit 10000` with a fresh batch ID and dedicated topic to reproduce the small sample; prepare/import references bound to that exact event manifest, submit on YARN, export with `scripts/export-batch.sh HDFS_BATCH NEW_DEST SPARK_EVIDENCE_JSON`, then publish using `retailrocket publish --store STORE --replay REPLAY --export EXPORT`. Launch `streamlit run retailrocket/dashboard.py -- STORE`.

Original events SHA256 is `3745aa83238b1e6d44d8fda209807899f420084398f94ddf745f3cbcfecbf9e7`, with2,756,101 data rows. The first10,000 rows have9,661 views,250 addtocart and89 transaction events. The original baseline execution evidence is [small-sample.md](../evidence/small-sample.md); it explicitly records the baseline source revision rather than claiming later features were present.

The default bounded resource settings request two executors of512MiB heap+384MiB overhead, one core each, and a512MiB AM. Per-job JVM class-space and code-cache reservations are capped at64MiB each, preserving existing YARN virtual-memory enforcement. The initial attempt without these caps was killed by that enforcement. Final evidence must include successful tasks on different executor hosts, successful YARN status, HDFS files and DuckDB result counts.

Clock audit: at host UTC2026-10-19 05:43, guests reported UTC2026-10-18 21:43 (eight hours behind). Guest local logs displayed05:43 because of their timezone. No guest clock was changed during jobs. `replay_time` records the observed guest clock and must not be interpreted as calibrated ingestion latency; historical `event_time` derives source epoch milliseconds in UTC. Synchronize guest clocks separately before a timing demonstration.
