## V1：历史数据分析与批处理看板（已完成）

2026-10-19 已完成实现、合并至主分支并通过全量验收，关联规格及任务 #1–#8 已关闭。完整的 2,756,101 条行为经过 Kafka 和 HDFS，Spark 在 YARN 跨节点执行；28 项测试及定向回归、看板与发布恢复验证通过。详见 [全量验收证据](evidence/full/README.md)。以下为已交付的 V1 范围。

### 1. 项目目标

在当前本地机器上，复用现有三节点 Hadoop / Kafka 集群，以 [Retailrocket 公开电商数据集](https://www.kaggle.com/datasets/retailrocket/ecommerce-dataset)为唯一数据源，实现历史行为回放采集、分布式存储、离线清洗分析和交互式可视化，构建可解释的用户行为画像。

项目必须实际使用 Kafka、HDFS 和 YARN 上的 Spark 分布式计算。V1 以快速完成可运行系统为目标，手动触发批处理，不要求实时更新。

### 2. 数据采集与处理任务

1. 使用 Python 将浏览、加购、购买事件从原始 CSV 回放至 Kafka，保留原始事件时间，记录回放时间、数据版本、源文件和源行号。明确标注历史数据回放，不作为真实实时访问展示。
2. 回放前记录各分区起始 offset，确认发送完成后记录结束 offset；Spark 按确定范围批量采集至 HDFS 原始层。
3. 商品属性和分类树直接导入 HDFS，与行为数据绑定同一数据版本。
4. 使用 PySpark / Spark SQL 在 YARN 上执行清洗、去重、分类关联及分析，以 Parquet 保存明细和结果。
5. 将必要的访客粒度及聚合结果导出到本机，由 DuckDB 查询，Streamlit + Plotly 展示；看板不直接扫描 Kafka 或启动 Spark。
6. 开发使用固定小样本，最终验收处理完整行为数据。

### 3. 分析功能与指标口径

| 页面 | 必须实现的内容 |
| --- | --- |
| 行为概览 | 浏览、加购、购买事件数，独立访客数，按日趋势 |
| 转化分析 | 各行为独立访客数；浏览购买、加购购买的访客交集及占比 |
| 商品与分类 | 热门商品、热门分类、分类购买情况；匿名分类以原始编号展示 |
| 用户画像 | 活跃天数、事件次数、购买次数、最近活跃间隔、按浏览次数排序的分类偏好；购买行为单独展示 |
| 数据质量摘要 | 输入与有效记录数、异常记录数、疑似重复数量、分类关联覆盖率 |

- 所有分析以 UTC 原始事件时间为准，界面标明时区；日期筛选统一影响全部页面和画像。
- 转化指标为所选范围内的浏览购买交集除以浏览访客数、加购购买交集除以加购访客数。不要求行为顺序，不称为严格漏斗；分母为零显示无数据。
- 跨日独立访客和交集按访客去重，不能直接累加每日人数。
- 最近活跃间隔以筛选范围内最大事件时间为基准，无行为访客不进入当前画像列表；提供访客 ID 查询和分页。

### 4. 数据质量与批次可靠性

- 商品分类关联不晚于行为发生时间的最近分类记录；无匹配时保留为未知分类，不用未来记录补齐，并统计关联覆盖率。
- 时间无法解析、缺少访客或商品标识、行为类型不合法的记录隔离并统计，不进入正式指标；原始记录保留。浏览与加购缺少交易标识属于正常情况。
- 采集重试产生的同一源记录只计一次；源文件不同行中的相同内容保留，报告疑似重复数量。
- 每轮采集与分析建立独立批次，登记数据来源、Kafka offset 范围、记录数、处理状态和输出位置。同一批次重跑不重复累计。
- 每个发布批次为指定输入范围的完整快照；失败批次可重试，不覆盖此前成功结果。看板只读取最近成功发布的批次，显示批次及数据时间范围，缓存按批次和筛选条件区分。
- Kafka 用于采集传输，原始文件及 HDFS 原始层用于持久保存与重算，不依赖 Kafka 无限期保留消息。

## V2：实时数据流与 React 页面交互（规格已确认并发布）

2026-10-19 已确认 Q1–Q19、整体方案及测试边界，规格已发布为 [v2-spec #9](https://github.com/nanfxqs/ecommerce-analytics/issues/9)，标记 ready-for-agent。以下为整理后的 V2 范围，尚未开始实现；性能数值仍须通过前置验证锁定。规格与后续任务以 GitHub Issues 跟踪。

### 交付范围

- React 页面、原始流监控、清洗后持续分析均为 V2 必选交付，分阶段验收，全部通过后才标记 V2 完成。历史分析保留 V1 全部已验收能力。
- 持续更新的业务指标限定为事件数、独立访客数、行为趋势，并持续更新质量统计；购买交集、商品分类及完整画像保留历史查询，暂不要求实时化。实时指标沿用 V1 计算口径，统计范围见下文。
- 历史回放提供可配置速率以及暂停、继续、停止操作，默认采用适合现场观察的加速回放，不要求按原始时间间隔等待。验收覆盖正常运行、制造积压和中断恢复；轮次边界见下文。

### 回放控制与统计口径

- 每个回放轮次选择确定的数据范围，播放一次后结束，不自动循环；再次演示建立新轮次，实时统计独立计算。同一时间只允许一个回放轮次运行。
- 实时业务指标统计本轮已处理的全部有效数据，行为趋势按原始事件时间 UTC 分日展示。实时页暂不提供任意日期筛选，历史页保留 V1 完整筛选能力；速率与积压等过程监控使用当前处理时间。
- 暂停只停止发送新消息，处理端继续消化积压；继续从暂停位置发送。停止结束本轮发送，待已发送数据处理完成后标记“提前停止”，不得视为原计划范围的完整结果。
- 本轮范围内按源记录身份精确去重，合法乱序事件全部纳入，不因迟到丢弃；源文件不同行的相同内容继续沿用 V1 口径保留。处理完成后，与相同输入范围的 V1 对应指标核对一致；资源不足时优先降低回放速率。
- React 页面提供速率设置、启动、暂停、继续、停止及操作结果展示；命令行保留用于排障与复现。

### 结果发布、恢复与性能目标

- 正常回放结束并消化完积压后，自动执行完整历史分析，通过校验后才切换历史结果；失败保留此前成功结果。提前停止的轮次仅保留监控与实时结果，不自动发布到历史分析。
- 持久保存轮次、发送进度与处理检查点；服务重启后由用户点击恢复，继续同一轮。允许恢复时重发少量消息，最终计数通过去重保持一致；检查点损坏时明确报错，不静默从头累计。关闭浏览器不停止后台回放或处理。
- 先进行性能验证，再锁定验收值。初始目标为页面每 2 秒刷新，正常负载下业务结果可见延迟 P95 不超过 10 秒，连续运行至少 15 分钟且积压不持续增长。报告必须记录输入速率、资源配置及校时方式；未达目标时调整方案，或重新确认门槛，不直接降低标准。
- V2 面向本机单人演示，页面与控制 API 默认仅监听本机地址，不增加账号权限体系；远程访问不属于本轮范围。

### 系统与页面设计

V2 采用本机 FastAPI 服务提供 HTTP 查询与回放控制，前端每 2 秒轮询。流处理使用 YARN 上的 Spark Structured Streaming，检查点保存在 HDFS；先验证精确去重、中断恢复与资源占用，再开展完整实现。

回放期间运行流任务；正常结束并处理完积压后，保存最终实时结果、释放流任务资源，再启动历史批处理，避免两个 Spark 作业争抢资源。新历史结果发布前，历史页面继续展示此前成功批次。

原始流监控分别展示生产确认速率、Kafka 各分区末端 offset、已成功提交的处理检查点 offset 和结果更新时间。积压按各分区 Kafka 末端 offset 与已成功提交处理进度的差值计算。最近消息样本最多展示 20 条，明确标注清洗前数据；不提供全量消息浏览与搜索。

页面采用 Ant Design + ECharts，默认浅色、中文桌面端布局，区分实时监控与历史分析导航。统一显示历史数据回放标识、轮次或批次、时间范围、更新时间及完整性状态；适配常见桌面窗口，移动端专门布局与主题切换不纳入 V2。

在 V1 已验证的数据口径和分布式链路上，增加可持续更新的数据流展示，并重建页面交互与视觉布局。数据源仍为 Retailrocket 历史行为回放，界面必须标明“历史数据回放”，不将它描述为真实用户正在访问商城。

| 展示位置 | 计划内容 | 指标用途 |
| --- | --- | --- |
| 清洗前：原始流监控 | 接收速率、累计消息量、分区 offset、处理进度与积压、最近消息样本 | 观察采集链路，不作为正式业务统计 |
| 清洗后：质量与业务分析 | 持续更新有效、异常、重试去重数量与原因，以及事件数、独立访客数和行为趋势 | 使用清洗后的结果，沿用 V1 业务口径；购买交集、商品分类及完整画像保留历史查询 |
| 历史分析 | 保留 V1 已验收的概览、购买关联、商品分类、画像与质量查询能力 | 提供历史结果与实时结果的核对基准 |

接收时间用于观察回放与处理过程；原始事件时间继续按 UTC 用于历史业务分析。两种时间轴分别标注。实时结果展示处理进度、最近更新时间及结果是否完整，避免与 V1 已成功发布的完整批次混淆。

### 输入、保留策略与验收

- 页面仅选择已准备并校验的数据版本，提供固定小样本和完整数据两种范围，不提供上传或任意区间裁剪。完整数据验收处理 2,756,101 条原始行为，核对与 V1 对应指标。
- 不自动删除轮次结果、检查点及历史批次；交付文档化的手动清理命令，禁止清理活动轮次和当前已发布批次，页面不增加删除功能。
- 端到端结果可见延迟从消息获得 Kafka 发送确认起，至包含该消息的统计结果首次在页面显示止。性能验证使用可追踪测试事件并校准时钟；故意制造积压和故障恢复阶段单独报告，不混入正常负载 P95。
- 验收必须覆盖完整数据正确性、至少 15 分钟稳定运行、重复消息、异常与乱序、跨日访客、暂停与继续、提前停止、积压及消退、中断恢复、检查点损坏显式报错，以及历史发布失败保护。
- 记录实际 Kafka / HDFS / YARN 执行证据，确认流任务与历史批任务实际跨节点执行；所有必选交付通过后才将 V2 标记为完成。

- [ ] 完成视觉、交互、端到端更新及真实跨节点运行验收，再将 V2 标记为完成。

### 与 V1 架构决策的关系

[ADR 0002](adr/0002-kafka-batch-ingestion.md) 记录的是 V1 的手动批处理决策，当前仍适用于已交付系统。V2 的持续流处理及独立前端 / 查询接口将扩展该边界；已确认的架构取舍见 ADR 0003，后续接口、状态存储和输出布局应遵守本文规格，并在实现设计中补全。V2 的规划不表示这些能力已经实现，也不改变 V1 的验收事实。

V2 已确认的有界回放与流批分阶段运行取舍见 [ADR 0003](adr/0003-bounded-streaming-replay.md)。
